# 为什么 SEO 检测应该放在发布之前

主流 SEO 工具的工作方式是**爬取已上线的站点，然后报告问题**。
Ahrefs、Semrush、Screaming Frog 都是这个模式。它有一个共同前提：
问题已经存在于线上了。

这个前提值得质疑。

## 发布后审计的三个代价

**损失已经发生。** 一篇缺少 title 的文章上线两周，
这两周的所有展现机会都浪费了。审计报告只是告诉你「你已经损失了」。

**修复要走完整流程。** 发现问题后需要找到作者、修改、重新审核、
重新发布，还可能要处理已经被索引的错误版本。相比之下，
发布前修改只需要改一次。

**重复犯错。** 审计是周期性的，两次审计之间发布的内容不受约束。
同一个人可能连续发布十篇都缺 description，直到下次审计才被发现。

## 前置检测的做法

把检测放进发布流程，并且**设为强制**：

```
提交内容 → 规则检测 → 有严重问题？
                        ├─ 是 → 拒绝发布，返回具体问题与修复建议
                        └─ 否 → 允许发布
```

关键在于「强制」二字。如果检测结果只是提示，
赶进度时一定会被跳过——这不是纪律问题，是人性问题。

## 强制门槛的设计要点

### 只拦真正致命的问题

如果所有问题都阻止发布，这个门槛会立刻被绕过或关掉。
必须区分等级：

- **阻断发布**：缺少 title、正文为空、页面带 noindex、
  canonical 指向其他域名——这些会导致页面完全无法获得流量
- **不阻断**：描述过长、缺少 og:image、标题层级跳跃——
  这些影响效果但不影响收录

经验上阻断项应该控制在总规则数的 20% 以内。

### 门槛必须无法绕过

检测逻辑如果写在接口层，绕过它只需要调用另一个接口。
正确的位置是**领域模型内部**——无论从 HTTP 接口、后台任务
还是命令行触发发布，都必须经过同一段判定。

### 报告必须可执行

「SEO 评分 62 分」对修复没有任何帮助。有用的报告包含三部分：

- **问题**：具体是哪条规则
- **证据**：为什么判定为问题，比如「title 长度 78 字符，建议不超过 60」
- **修复方向**：具体要做什么

再加上**预估耗时**和**修复后能提升多少分**，
就可以按性价比排序，先做花时间少、收益大的。

### 信息不足时跳过，不要猜

如果解析器没能提取到链接文本，正确做法是跳过「锚文本无描述性」这条检测，
而不是报告「所有链接都没有描述性文本」。

误报的代价远高于漏报：一旦用户发现报告里有假问题，
整份报告的可信度就没了，之后真问题也会被忽略。

## 与 CI 的相似之处

这套做法和代码质量门槛是同一个思路：

| 代码 | 内容 |
|---|---|
| 单元测试不通过，不允许合并 | 严重 SEO 问题，不允许发布 |
| Lint 警告，提示但不阻断 | 优化建议，提示但不阻断 |
| 测试报告指出具体失败用例 | 检测报告指出具体规则与证据 |

没有人会质疑「测试不过不许合并」，但内容发布长期缺少同等约束。

## 局限

前置检测能保证的是**技术层面没有明显缺陷**。它不能保证：

- 内容会被收录——Google 官方明确不作保证
- 排名会提升——取决于内容质量、站点权威度与竞争程度
- 流量会增长——那是排名的结果

它解决的是「因为技术疏忽而白白损失机会」这一类问题。
在竞争激烈的领域，技术层面没有短板是必要条件，但不是充分条件。

判定标准参照
[Google 搜索基础规范](https://developers.google.com/search/docs/essentials)
与 [schema.org](https://schema.org/) 结构化数据标准。
Google 在其文档中明确写明不保证抓取与收录，也不接受付费提升排名——
任何声称能保证排名的服务都与官方说明相悖。
