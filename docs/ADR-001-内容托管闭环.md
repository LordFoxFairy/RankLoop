# ADR-001：从「抓取诊断」转向「内容托管闭环」

- 状态：已接受
- 日期：2026-08-06
- 影响文档：`RankLoop-SEO-项目完整.md` §1.1、§3.3、§3.5、§6、§7、§8.1

## 背景

原规格假设平台**抓取外部站点**做诊断，内容始终在用户自己手里。对齐后确认的实际诉求是：

> 平台托管内容；第三方通过 API 提交内容，平台跑 SEO 规则告诉它哪里不合格；
> 第三方自行优化（含使用自己的 AI）后重新调 API 更新，反复迭代直到达标发布。

平台**不介入 AI**，不生成内容，只提供接口与判定。

## 决策

### 1. 平台托管内容正文

内容进入平台数据库，这是托管的前提。原 §8.1「不把原始 HTML 无限制写入数据库」
仍然适用于**爬虫抓取的外部页面**，不适用于用户主动提交的托管内容。

### 2. 闭环形态

```text
第三方 POST 内容
  → 平台存储 + 跑 SEO 规则
  → 返回不合格项（规则编码 + 证据 + 修复建议）
  → 第三方自行优化后 PUT 更新
  → 重新跑规则（可多轮迭代）
  → 达标 → publish
  → 投递 + IndexNow 提交
```

与原 §1.1 的差异：**不需要重抓验证**。内容在平台手里，规则直接跑，
判定即时且确定。原闭环的「用户修复 → 平台复检」压缩成一次 API 调用。

### 3. 内容格式：HTML 与 Markdown 双支持

- `html`：直接解析，可跑全部规则。
- `markdown`：存原文，平台渲染为 HTML 后跑规则。

**Markdown 的元数据由 frontmatter 提供**（`title` / `description` / `canonical` /
`robots` / `og:*`）。因为平台负责渲染，`<head>` 由平台生成，所以原先担心的
「MD 没有 head，半数规则失效」在托管模式下不成立。

缺失 frontmatter 时按缺失对应元数据处理，并在响应中列出 `skipped_rules`
及跳过原因 —— 不得因输入格式限制而产生假阳性问题（遵循 §0 第 10 条）。

### 4. 发布门槛

- `critical` 问题存在时拒绝发布，返回 `422 SEO_GATE_FAILED` 并列出阻塞规则；
- `warning` / `notice` 仅提示，不阻塞。

### 5. 投递目标抽象（关键，避免返工）

「内容最终发布到哪个域名」这一决策**尚未确定**，因此抽象为 `PublishTarget`：

| 实现 | 说明 | 阶段 |
|---|---|---|
| `platform` | 发布在平台自有路由下 | MVP |
| `webhook` | 通知第三方自行拉取并发布 | 二期 |
| `git` / `cms` | 平台代为推送到用户站点 | 二期，需评估与 §3.6 的冲突 |

正文存储、规则引擎、发布状态机三者与投递方式**完全解耦**，
后续新增投递实现不需要改动数据模型。

**后续落地（2026-08）**：域名方案已确定为 `<slug>.<平台域名>` 一级子域名。
不用二级（`<slug>.rankloop.<域名>`）有两个原因：
Cloudflare 免费版通用证书只覆盖一级子域名，二级会握手失败；
层级越浅越利于 SEO。自有域名验证归属后优先生效，权重积累在客户自己的域名下。
`webhook` 投递也已实现（签名 + 重试 + SSRF 防护）。

### 6. 爬虫推迟到第二期

MVP 只做托管闭环。规则引擎设计成**输入无关**——只接收 HTML 字符串与元数据，
不关心来源是托管内容还是爬虫抓取结果。因此第二期接入爬虫时规则引擎无需改动。

随之推迟：SSRF 防护（§8.1）、网站所有权验证（§3.2）、`crawl_*` 相关表。
这三项是原规格中最复杂的部分，推迟可显著加快 MVP 与 Docker 镜像交付。

**注意**：SSRF 防护在二期接入爬虫时必须完整实现，仍是最高优先级安全项。

### 7. Webhook 采用轻 payload

事件只携带 `event`、`site_id`、资源 ID 与拉取链接，第三方凭 API Key 回调获取详情。
避免大站点 payload 膨胀，且重试时拿到的始终是最新状态。

## 后果

**新增数据模型**（原 §6 未覆盖）：

```text
contents              # 正文、格式、状态、workspace_id
content_versions      # 每次更新一版，可回溯
content_checks        # 每版的检测结果与健康分
publish_targets       # 投递配置
```

**暂不实现**：`crawl_jobs`、`crawl_pages`、`page_links`、`page_snapshots`、
`site_verifications`（均属二期爬虫范畴）。

**保持不变**：多租户隔离（§2.2）、API Key 哈希存储、审计日志、配额、
IndexNow（§3.7）、Google Search Console 集成（§3.8）—— 这些与托管/抓取无关。

## 未决问题

1. **托管内容的最终 URL 归属**：平台域名下，还是投递回用户自有域名？
   已通过 `PublishTarget` 抽象隔离，不阻塞 MVP。
2. 是否需要内容编辑界面，或仅通过 API 操作。MVP 假定仅 API + 只读查看界面。

## 补充决策（2026-08-07）

ADR 撰写后的实现过程中产生了以下决策，一并记录以免规格与实现脱节。

### 8. 新增静态站部署形态（免费路径）

除原有的「API + PostgreSQL」托管形态外，新增**静态站生成器**：
`content/*.md` → 跑同一套 SEO 规则 → 通过门槛的内容构建成静态 HTML →
部署到 GitHub Pages 或 Cloudflare Pages。

原因：Docker 形态需要服务器与数据库；静态形态**完全免费**，
适合内容站与文档站，且 SEO 门槛与 API 形态共用同一个规则引擎
（`packages/seo-rules`），判定结果一致。

两种形态并存，用户按需选择。

### 9. 不引入渲染框架

评估过 Astro / Next.js，决定不用。本项目的核心价值是 SEO 规则引擎与发布门槛，
渲染只需输出语义正确的 HTML。引入框架会带来数百个依赖、独立构建步骤与版本维护成本，
与「零依赖、一键部署」冲突。

改为**配置外置**：`rankloop.config.json` 驱动导航、首页 hero、配色、字体、
页脚与自定义 head 标签，改外观不需要碰代码。需要复杂页面时可直接在
`content/` 下放 `.html`，构建时原样输出并照常参与 SEO 检测。

### 10. Google Search Console 全自动化

关键发现：Site Verification API 支持 **FILE 验证方式**，而本项目本身就是静态站生成器，
因此可以把验证文件写入构建产物随站点一起部署，实现**全自动验证**，无需人工进控制台。

流程：取令牌 → 写入产物 → 部署 → 请求校验 → 添加站点 → 提交 sitemap → 回读确认。
首次发布时验证文件尚未上线，校验会失败一次，属预期行为，日志如实说明且不阻断发布。

### 11. 关于「自动化 Google 收录」的边界

必须如实记录：**Indexing API 对普通网页不开放**，官方限定
`JobPosting` 与 `BroadcastEvent` 两种类型。因此「发布即被 Google 收录」
对文章类内容在技术上不存在。

可自动化的只有：拦截 SEO 缺陷、生成合规 HTML 与 sitemap、提交 Search Console、
通过 IndexNow 通知 Bing/Yandex（Google 不参与该协议）。
收录时间与排名由 Google 决定，任何工具都无法强制。

详见 [Google-SEO-自动化说明.md](Google-SEO-自动化说明.md)。

### 12. URL 规范化（线上发现的问题）

真实部署后发现两个只在生产环境暴露的问题：

- **主机名大小写**：`github.repository_owner` 保留原始大小写，
  而实际域名为小写。Google 会把两者视作不同 URL，造成重复内容。
  已在 workflow 与配置加载两层统一转小写。
- **目录索引 301**：静态托管把 `/rules` 重定向到 `/rules/`。
  sitemap 与站内链接若使用无斜杠形式，会让 Google 多跑一跳并浪费抓取预算。
  已统一使用带尾斜杠的最终 URL。

两项均有回归测试锁定。
